# 文档设计

## Context

现有主线已具备 VPC 配置、接入与校验基础，v3.4 工作台在同日并行开发 / 收尾。用户要求独立的高层蓝图，由其他开发者分块落地，Codex 保持前端设计与关键后端方案审核责任。

## Decisions

1. 采用根目录 `PRD-VNEXT.md` 作为 A 类产品文档，NEXT 不绑定正式版本号。
2. 一份主文档先讲总方向，最后给出一期范围；避免同时维护两份重复的总 / 分 PRD。
3. 一期暂建议已有 VPC 的接入与验证故事；将完整三维、长期差异与意图保障留在后续阶段。
4. 固定产品语义与验收，不提前固定数据库表、API 路径、容器或 change 数量。
5. 新增规格仅约束蓝图文档应包含什么，不把未来产品需求直接并入已实现的 SDN 主规格。
6. README 与路线图只增加草案入口，不清理或重写与本请求无关的历史段落。
7. 以 change 内 `collaboration.md` 承担一期交接和反馈，由 PRD §9.4 指向当前入口。不新增第二份一期 PRD，不复制实施 tasks；跨工作区同步和会话通知显式处理，不暗示自动互通或后台监听。归档前迁移活跃事项并更新入口，历史记录保留。

## Risks And Trade-offs

- 概念样机可能让人误以为完整功能已有：文档明确离线演示与真实运行的区别。
- 现有阶段状态可能变动：后续实施必须核对最终交付的接口契约，不依赖本次工作副本。
- 小块委托容易丢失联动：以 N1 需求编号、输入输出语义、失败边界和证据作为交接依据。

## Validation And Approval

检查新增文档的相对链接、范围与状态一致性、OpenSpec 格式和改动边界。本 change 不含运行代码，不触发设备操作或全量应用 QA。

文档保持 Draft；用户未确认一期范围和开始收尾前，不归档、不提交、不推送。阶段实现另行立项。
